

# モノの記憶 (Technical Specification / README)

本ソフトウェアは、画像特徴抽出モデルを用いた物体照合によってアクセス制御を行い、端末ローカル環境でファイルおよびテキストデータを保持・暗号化エクスポートするWebアプリケーション（PWA）です。

---

## 1. システム構成・動作環境

* **種別**: Progressive Web App (PWA) / シングルページアプリケーション
* **実行環境**: モダンブラウザ（Safari, Chrome等。Web Crypto API, IndexedDB, WebAssembly対応必須）
* **ネットワーク通信**:
  * 初回起動時のみ：推論エンジンおよび学習済みモデル重みファイルの取得（CDN経由）
  * 運用時：通信不要（完全ローカル動作。外部サーバーへのデータ送信処理なし）
  * Content-Security-Policyにより、スクリプト・通信先は `cdn.jsdelivr.net`（推論エンジン本体）および `huggingface.co` 系ドメイン（モデル重みファイル）に限定。それ以外のホストへの通信はブラウザ側で遮断される。

---

## 2. 動作原理とアルゴリズム

### 2.1 画像特徴抽出 (Feature Extraction)
* **モデル**: `DINO (Vision Transformer Small, Patch Size 16 / ViT-S/16)` 量子化ONNXモデル
* **入力前処理**:
  1. 撮影画像から中央領域を正方形にクロップ（Center Square Crop）。
  2. 800×800ピクセル（品質0.85）にリサイズ。
  3. モデル内部で224×224ピクセルに再サンプリングおよび正規化。
* **特徴量合成（ハイブリッドベクトル）**:
  1. モデル出力テンソルの形状（`[1, seqLen, hiddenDim]`）を実行時に読み取り、次元数・パッチ数をハードコードせず動的に決定する（現行モデルでは `[1, 197, 384]` = CLSトークン1個＋パッチトークン196個）。
  2. CLSトークン（大局的形状情報）を取得。
  3. 全パッチトークンの要素ごとの平均値（局所的テクスチャ情報）を算出。
  4. 両者を加算合成し、L2正規化を実行。
     $$\mathbf{v} = \frac{\mathbf{x}_{\text{CLS}} + \frac{1}{N}\sum_{i=1}^{N} \mathbf{x}_{\text{patch}, i}}{\left\| \mathbf{x}_{\text{CLS}} + \frac{1}{N}\sum_{i=1}^{N} \mathbf{x}_{\text{patch}, i} \right\|_2}$$
  5. 最終出力：384次元の単位ベクトル。

### 2.2 回転耐性（Gallery-side Augmentation）
* 登録時、基準画像（0°）からCanvas操作により90°、180°、270°回転した3画像を生成。
* 各画像から特徴ベクトルを抽出し、計4つの384次元ベクトルを1つのキーセットとして保存。
* 照合時は1回の撮影で得たベクトルに対し、登録側の各回転ベクトルとコサイン類似度を算出。

### 2.3 照合判定 (Matching)
* **類似度計算**: 正規化済みベクトル間の内積（コサイン類似度: $-1.0 \le s \le 1.0$）。
* **判定論理**:
  * 対象アイテムが保持する全ベクトル（登録アングル数 × 4回転）との類似度を計算。
  * 最大値（$\max(s)$）がアイテムに設定された閾値（標準: 0.75 / 厳格: 0.82 / 寛容: 0.70）以上の場合に認証成功と判定（OR条件）。
  * **この照合はあくまで「開く意図の確認」であり、下記3章の鍵導出とは独立している**（詳細は3.1参照）。

## 3. セキュリティと暗号化仕様

カメラによる現物照合（ファジーな一致判定）と、実際の暗号鍵の導出（厳密な一致が必要な秘密情報）は、役割を分離している。前者だけでは鍵は導出できない。

### 3.1 端末内保存時（安静時暗号化: Encryption at Rest）

* **鍵管理（ダイヤル式コンビネーション錠）**:
  * AES-GCM鍵は固定で生成・保存されるのではなく、**ユーザーが設定した「ダイヤルの組み合わせ」からPBKDF2で都度導出**される。
  * ダイヤルは16分割・4ラウンド。各ラウンドで停止位置（0〜15）と回転方向（右/左）を記録し、`位置+方向` を4回分ハイフン区切りで連結した文字列（例: `7R-3L-15R-9L`）を鍵導出の入力とする。
  * 初回設定時は、入力ミスによる恒久的なロックアウトを避けるため、同じ組み合わせを2回入力させ一致を確認する。
  * IndexedDBの`meta`ストアに保存されるのは**PBKDF2の塩（salt, 16バイト・秘密情報ではない）のみ**。鍵そのもの（CryptoKeyオブジェクトを含む）は一切永続化されない。
  * 導出された鍵は、同一セッション中（後述3.3のトリガーでクリアされるまで）のみJavaScriptのメモリ上にキャッシュされ、再利用される。これにより「現物照合に成功するたびに毎回ダイヤルを回す」という手間を避けつつ、鍵がアプリ起動中ずっと無条件に存在し続ける状態を回避している。
  * 連続した呼び出し（UIの誤操作等）でダイヤルが二重に開かないよう、鍵導出処理は進行中のPromiseを共有する排他制御を行う。
* **暗号化対象**:
  * `FILE LOCK`: 添付ファイルのバイナリおよびファイル名。
  * `MASKED` / `HIDDEN`: 名称、メモ、写真、添付ファイルのバイナリ全体。
* **暗号化形式**:
  * 暗号方式: AES-256-GCM
  * 鍵導出: PBKDF2 / SHA-256 / **310,000回**ストレッチング
  * IV: 12バイト（暗号化ごとに`crypto.getRandomValues`で生成、暗号文先頭に付与）
  * 認証タグ: 16バイト（GCM標準。誤った組み合わせを入力した場合、ここで検証エラーとなり復号できない）

### 3.2 外部エクスポート時（可搬暗号化ファイル: `.encbak`）

* **鍵導出**:
  * アルゴリズム: PBKDF2 / SHA-256 / 310,000回ストレッチング
  * Salt: 16バイト（エクスポートごとに乱数生成。3.1の塩とは別物）
  * パスワードはマスク入力モーダル（`<input type="password">`）から取得する（旧版の`window.prompt()`は画面に平文表示されるため廃止）。
  * **このエクスポート用パスワードは、3.1のダイヤルの組み合わせとは完全に別の秘密情報である。** バックアップファイルを復号できても、中の保護された記録を読むには別途ダイヤルの組み合わせが必要になる（次項参照）。
* **保護レベル別の書き出し方針**:
  * `STANDARD`：名称・メモ・写真・添付ファイルを平文のままBase64化して書き出す。
  * `FILE LOCK` / `MASKED` / `HIDDEN`：**現物照合・ダイヤル解錠の有無にかかわらず、常に暗号化された状態（ciphertextそのもの）のまま書き出す。** エクスポート処理が内部的に復号を行うことは一切ない。
  * 保護された記録が1件でも含まれる場合、3.1の塩（秘密情報ではない）をバックアップファイルに同梱する。これにより、復元先の端末にまだダイヤルが設定されていなければ、同じ塩を引き継いで元の組み合わせのまま開けるようにする。
* **暗号化形式**:
  * 導出鍵による AES-256-GCM 暗号化。
  * データ構造: `[Salt (16B)] + [IV (12B)] + [Ciphertext + Tag (可変)]`
* **オプション**: メモ文字列を除外し、添付ファイルのみを暗号化出力することが可能。
* **復元（インポート）**:
  * 保護されたままの記録は、復号を試みず暗号文のままIndexedDBへ書き戻す。元のダイヤルの組み合わせを入力しない限り、開くことはできない。
  * 新旧2種類のバックアップファイル形式（配列直下／`{items, vaultSalt}`形式）の両方を読み込める。

### 3.3 セッション管理
* 復号されたデータ（画像Blob、平文テキスト、ファイル実体）および3.1の導出済み鍵は、ブラウザのRAM（JavaScript実行コンテキスト内のMap／変数）にのみ保持される。
* 以下のトリガーで、RAM内の復号キャッシュ・セッションID（Set）・導出済み鍵を同時にクリアする：
  1. 「一覧に戻る」ボタンの押下
  2. 下部ナビゲーションによるタブ切り替え
  3. ブラウザの`visibilitychange`イベント検知（タブの非アクティブ化、アプリ最小化、タスクスイッチ）

## 4. 機能仕様

### 4.1 保護レベルの定義

| レベル | 一覧での表示 | IndexedDB上の保存状態 | アンロック条件 |
| :--- | :--- | :--- | :--- |
| **STANDARD** | 写真・名称を表示 | 平文 | 常時アクセス可能 |
| **FILE LOCK** | 写真・名称を表示 | 写真・名称は平文、**ファイルのみ暗号化** | カメラ照合 → ダイヤル解錠でファイル閲覧・取得可 |
| **MASKED** | 写真・名称を伏字化 | **写真・名称・メモ・ファイルを暗号化** | カメラ照合 → ダイヤル解錠で全項目がRAM上に展開 |
| **HIDDEN** | **一覧から除外** | **写真・名称・メモ・ファイルを暗号化** | カメラ照合 → ダイヤル解錠時のみ検知・RAM上に展開 |

STANDARD以外の保護レベルを初めて設定する際、ダイヤルの組み合わせが未設定であれば、その場でセットアップ（2回入力）フローに移行する。

### 4.2 マルチキー登録（OR条件認証）
* 1つの記録IDに対して、複数の写真（および各4回転ベクトル）を追加登録可能。
* 登録されたキーのいずれか1つと合致すれば照合成功とみなす。
* 詳細画面では登録済みキーのサムネイルをタップしてプレビューの切り替えが可能。

### 4.3 重複検知
* 撮影直後、登録済みの全ベクトルと照合を実行。
* 類似度が0.82以上の既存データが存在する場合、警告を表示し、既存データの閲覧または強制保存の選択を要求。
* 衝突対象が`MASKED`または`HIDDEN`の場合、名称を出力せず「保護された記録」と表示する（この判定は復号を伴わず、暗号化されたままのレコードのメタ情報のみで行う）。

## 5. 撮影条件とモデル特性

### 5.1 推奨撮影条件
* **被写体サイズ**: 画面の50%〜70%を被写体が占める画角（背景面積の比率を下げるため）。
* **背景**: 単一色またはテクスチャの少ない面。近傍に文字印刷物や別の独立した物体を置かないこと。
* **無地物体**: ロゴ、印字、境界線など幾何的特徴のある面を撮影面とする。

### 5.2 DINOモデルの認識特性
* 画素（RGB）の絶対値ではなく、境界・エッジ構造およびパッチ間のアテンション（関連度）を重視して特徴量を抽出する。
* **挙動の例**: テレビを被写体とした場合、画面内の放映映像が変動しても、外枠（ベゼル）、アスペクト比、スタンド等の構造的特徴量が支配的となるため、同一物体として判定される。

## 6. 制約事項と留意点

1. **データ永続性**:
   * データはブラウザのIndexedDBに依存。ブラウザ側で「サイトデータ消去」や「履歴削除」を実行した場合、データは消去される。
   * iOS Safari等の仕様により、端末ストレージ容量が極度に逼迫した場合にブラウザデータがOSによって整理される可能性があるため、定期的なエクスポート（`.encbak`）が必要。
2. **秘密情報の不可逆性**:
   * ダイヤルの組み合わせ、およびエクスポート時に設定したパスワードは、いずれもハッシュ化等の形でも保存を行わない。**忘失した場合、該当する保護記録・バックアップファイルを復元する手段は存在しない。**
   * この2つは別々の秘密情報である点に注意（3.2参照）。
3. **ストレージ容量**:
   * 添付ファイルはBase64シリアライズおよびBlob経由でIndexedDBに格納される。数百MB以上のファイルを多数保持するとブラウザのストレージクォータ制限（QuotaExceededError）に抵触する。
4. **脅威モデル上の限界**:
   * カメラによる現物照合は「開く意図の確認」というUX上のゲートであり、暗号学的な防御そのものではない。実際のアクセス制御はダイヤルの組み合わせ（3.1）が担っている。
   * ダイヤルの組み合わせ空間は16通り×4ラウンド×方向2種（概算で約100万通り）であり、長大なランダムパスワードと比較すると強度は限定的である。本アプリは「総当たり耐性の高い金庫」ではなく、「手軽さと現物照合という体験を優先した、端末紛失・覗き見・BACKUP機能の悪用に対する現実的な抑止」を目的として設計されている。
